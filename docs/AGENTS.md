# docs/AGENTS.md — 文档标准与索引

本文件只约束 `docs/` 内的技术文档。仓库级开发规则见 [根目录 AGENTS.md](../AGENTS.md)；项目介绍见 [README.md](../README.md)。以下文档把计划契约与已实现行为并列描述，每个单项以代码、测试和实测结果为准，不能仅凭文档声称功能已经运行。

## 文档结构与归属

- 每项事实只在负责它的文档中详细说明；上层文档只描述直接组成、职责和主要行为，并链接到下层文档。文档类型不能扩大它的主题范围。
- 写作前确定读者要查阅当前契约，还是要按步骤完成任务。参考文档按主题组织，教程按先决条件到结果组织；若两类内容都较多，应拆成独立文档，少量混合内容则标明小节。
- 教程先交代读者需要的知识与环境，再按依赖顺序推进；高级内容放到后续教程或参考页。步骤必须包含可执行的验证方式，不能把规划命令当作已可运行的入口。
- [架构设计](architecture.md)只承担系统组成、主要数据流和进程边界；接口字段、数据库约束、解析细节、测试机制和部署配置由各自专题文档负责。实施步骤归 [开发约定](development.md)，阶段范围归 [技术实施顺序](roadmap.md)。
- 长期有效的决策理由属于 Agent Note，当前技术契约留在 `docs/`；采用 Agent Note 时再建立对应目录与索引。现有 [技术选型](technology-decisions.md)记录尚待验证的方案取舍，不能当作已实施决策记录。

## 写作与检查

- 明确区分规划、已实现行为和实测结果。实现后把相应契约更新为当时的实际行为；历史取舍留在决策记录，不在当前文档里堆叠变更过程。
- 每个普通段落占一个物理行，依靠编辑器软换行；表格、列表和代码块按 Markdown 结构排版。直接写明主体、操作、条件、失败行为和限制，删除重复规则、实现推理过程与不必要的强调。
- 代码示例注明适用环境；真实命令和文件路径须能在仓库中核对。仓库目前没有文档字数、类型检查或链接门禁，不写入不存在的 `verify-*` 命令或假定它们已经通过。
- 使用相对 Markdown 链接引用当前文件；新增、删除或更名文档时更新本索引，并检查受影响的本地链接。字数保持简洁，但不为没有配置和执行器的预算写虚假的上限。
