# 检索、问答与引用

> 本文大部分是待实现的技术契约；inference 查询编码（`kind=query`）已由隔离模型 tester 在真实权重与真实 HTTP 上验收，`POST /api/v1/retrieval/search` 已把 API 侧受限查询客户端与中文关键词分析器接到同一授权 SQL：向量路（pgvector exact `<=>`）与关键词路（`plainto_tsquery('simple', :terms)` + `ts_rank_cd`）各取 top-20，按 RRF（k=60、`chunkId` 去重、最多 40）融合并返回两路排名/分数与融合名次；该路由只做检索，不含 LLM 生成、相似度阈值与多轮。可降级神经重排（`bge-reranker-base`）已实现但**默认关闭**，且未做真实模型验收（见下文“可降级重排”）。神经重排属于 Phase 2 完整范围。中文关键词分析器仍为纯函数（`analyze()`，构造需一次性私有临时目录 IO），只在查询侧被调用。证据问答主流程（会话、历史、追问、引用）已实现，见下文“生成和结构校验”。

## 编码与关键词索引

计划使用固定 revision 的 `BAAI/bge-small-zh-v1.5`，512 维，余弦距离，CPU 推理。查询与文档须使用同一已登记的编码契约；换模型、维度或规范化设置时另建 index profile。inference 已实现受限的内部查询编码（`kind=query`）：服务端在编码前对每条查询**恰好追加一次**官方检索 instruction 前缀 `为这个句子生成表示以用于检索相关文章：`，token 计数与向量都基于追加后的完整模型输入（含前缀与特殊 token），不截断，超过模型 512 个位置上限时返回显式 422（已由隔离模型 tester 在真实权重与真实 HTTP 上验收：`query(text)` 与 `document(prefix+text)` 向量逐元素差 0、token 相同，512 token 200 / 513 token 422 且不截断）；`kind=document` 路径与文档向量完全不变，因此现有七个字段的 index profile `config_hash` 不变。查询响应携带 wire 字段 `queryEncodingContract='bge-zh-query-v1'`（`citemind_inference.config.QUERY_ENCODING_CONTRACT`），文档响应省略该字段。该具名契约与固定前缀由独立 literal golden 测试钉死（改动实现而不同步 golden 会失败），它只做回归检测、不能自证前缀一定正确；仅凭 `modelRevision` 无法识别 instruction 漂移，改变前缀、追加位置、计数方式或查询编码策略都必须提升该契约版本并重新评估，不能静默切换。用户输入本身以该前缀开头时服务端不去重、不改写，前缀仍只追加一次。API 侧另有受限查询客户端 `rag_backend.retrieval.query_embedding_client`（已由 `POST /api/v1/retrieval/search` 接线；单条、零自动重试、只连内部 inference、本地字符/字节上限按完整模型输入（前缀 + 用户查询）折算、严格要求响应 `queryEncodingContract` 精确匹配且校验 512 维有限 L2 归一化向量、revision 一致与整数 1..512 的 `tokenCounts`，不导入 tokenizer/worker 身份）。检索只在 KB 的 `active_index_profile_id` 指向的 profile 上进行：该 KB 尚无 READY 索引时指针为 NULL、该 KB 不可检索，全局登记的默认 profile 不能替代它；该默认契约由 `rag_backend.models.profile_contract` 冻结（规范 JSON 与 `config_hash` 为纯计算，`default_index_profile()` 调用含有限私有临时目录 IO；`config_hash=4af4c33d…57fa`，完整 golden 见 [入库与版本](ingestion.md)）。入库侧另有纯身份预检模块 `rag_backend.ingestion.identity_preflight`（独立 reviewer APPROVED 与独立 tester 已验收、未接线）：它只判定 job/profile/parser 身份一致性，`ALLOWED` 不等于 READY 或可检索，检索仍只按 `active_index_profile_id` 关联的 READY generation 与 `chunk_embedding`。入库侧另有 worker 专用工厂 `rag_backend.ingestion.worker_index_identity.initialize_worker_index_identity`（未接线；独立 tester 已在真 worker 镜像内验收）在显式调用时校验四件 tokenizer 资产并构造真实 `KeywordAnalyzer` 与 `IndexProfileContract`，其结果同样不代表 READY 或可检索。MVP 在 PostgreSQL/pgvector 内对已授权小语料做 exact search；HNSW 只有与 exact 基线比较过滤后的召回和延迟后才引入。

中文关键词路已实现分析器 `rag_backend.retrieval.KeywordAnalyzer`（`analyze()` 为纯函数，构造含私有临时目录 IO；由检索服务在查询侧调用，模块本身不连数据库）：固定 `jieba==0.42.1`，用私有 `jieba.Tokenizer` 的 `cut_for_search`，先做 NFKC + Unicode `casefold`，把英文标识、错误码、数字与下划线/连字符整段保留，过滤纯标点/空白/emoji，重复词项保留；原始输入与 NFKC 后长度都不得超过 `MAX_INPUT_CHARS=100000`，超限抛 `KeywordAnalyzerInputError`（与部署/资源类 `KeywordAnalyzerError` 区分）。分析器标识为精确形状 `jieba-0.42.1-search-v1:base-sha256=7197c321…12a8:v1-sha256=e3b0c442…7852b855:norm=NFKC+casefold`，同时钉死 jieba 自带 `dict.txt`（5,071,852 字节 + SHA-256）与领域词典（当前 v1 为 0 字节空词典，因无可授权真实术语，不编造企业词）。构造先在私有临时目录内初始化分词器、结束后立即清理，绝不读写共享 `temp/jieba.cache`（jieba 默认缓存对基础词典不做 mtime 校验，可被其他进程投毒）；**运行时必须能创建可写私有临时目录**（POSIX 0700、Windows 使用 per-user TEMP ACL），只读容器必须提供安全 tmpfs，否则静态 `KeywordAnalyzerError` fail closed，不为可用性回退共享缓存。文档与查询必须用同一分析器产出的词项流，再以参数绑定交给 PostgreSQL `to_tsvector('simple', ...)`，以 GIN 过滤和 `ts_rank_cd` 排序；**不是**把未切分的中文原句直接送 `simple`，也不能把空格连接的多词项流直接当 `tsquery`（会触发语法错误；隔离 PG 17 中单项 `gpt-4` 可解析），查询侧必须用绑定参数构造合法 OR/`plainto` 查询。真实 PG 17 实测（隔离库 `public` 零表、仅用 psycopg 绑定参数验证词项链路）：中文经 jieba 切分后与 `simple` 索引可互相匹配，未切分原句不匹配；`ts_rank_cd` 在合法 OR 查询下约 0.2、`plainto_tsquery` 下约 0.1；但 `simple` 会再切分标识——`error_code` 丢失下划线、结果近似 `error code`（两者不可区分），`gpt-4` 被拆成 `gpt` 与 `-4`，因此不声称精确标识检索。改动词典必须同时提升词典版本、文件名、SHA-256 与 profile，并新建 index profile 重索引，绝不能改变旧 profile 的含义；未来用 freq=0 新增词条会改全局 `jieba.finalseg.Force_Split_Words`，新词典版本必须单独做安全评估。词典 hash 是索引契约的一部分，`ts_rank_cd` 不是 BM25，原文引用仍用未归一化文本。本切片只产出词项流，未写 `chunk.fts`、未 seed 任何 `index_profile`（`knowledge_base.active_index_profile_id` 仍为 NULL）、当时尚无检索 API，因此文档仍不可检索。

## 授权候选与融合

1. 会话生成服务端 `AuthContext`：组织、用户、可访问 KB 和文档权限。请求的 `kbIds` 必须是其中的子集。
2. 对当前独立问题编码。向量路与关键词路在 SQL 中 JOIN 同一授权、未删除、有效版本、属于该 KB `active_index_profile_id` 的 READY generation 集合，各取 top-20；可用一条双路 CTE 或一个短 `REPEATABLE READ` 事务顺序查询，不能并行共享 AsyncSession。
3. 用 RRF 合并：`RRF(d) = Σ 1 / (60 + rank_i(d))`，一路未命中时不贡献分数。按 `chunkId` 去重，保留两路原排名、分数与融合名次，最多 40 个候选。参数 60 和 top-k 是初值，需在开发集调优。
4. 完整范围对融合后 top-10 调用 `bge-reranker-base`，按模型 tokenizer 控制 query+chunk 长度（`max_length=512` 截断）。超时或不可用时明确标记 `rerank_unavailable`，按融合排名继续，不能伪造重排分数。
5. 从最终排名选 4～6 个片段，同一文档最多 3 个；相邻 chunk 也必须重新受权并服从上下文预算。数据库事务在候选 DTO 取出后结束，不持连接等待模型。

已实现（授权混合检索首片）：`POST /api/v1/retrieval/search`（`rag_backend.retrieval.fusion`/`repository`/`service`、`rag_backend.api.retrieval`）落地上述第 1–3 步，不含第 4、5 步。请求体只有 `{"query","kbIds"}`，Reader 即可；组织与会话来自服务端，`kbIds` 必须是本次会话可访问集合的子集，否则统一返回不暴露存在性的 404 `KNOWLEDGE_BASE_NOT_FOUND`；`query` 的字符上限对齐查询编码客户端对完整模型输入（服务端追加前缀后）的实际限制，超长/空白在解析阶段就 422。`active_index_profile_id` 为 NULL 的 KB 不可检索、静默排除；请求范围内出现多个不同 active profile 时无法用同一次查询编码检索，返回 422 `RETRIEVAL_PROFILE_CONFLICT`。两条 SQL 用权威链 `chunk → index_generation → document_version → document → knowledge_base` 过滤组织、未撤销 `kb_member`、未删除文档、`document.active_version_id`、`READY` generation 与 `kb.active_index_profile_id`，并叠加文档 ACL（`document.acl_mode='INHERIT'` 或 `document_acl` 中登记 `USER`/`READ`，见 [安全](security.md)），不使用 `chunk` 上冗余的归属列；两路都要求 `chunk_embedding.profile_id` 与该 profile 一致。查询词项由 `KeywordAnalyzer.analyze()` 产出后以绑定参数交给 `plainto_tsquery('simple', :terms)`，在线程池内执行；查询向量以绑定字面量交给 `<=>`，不做字符串拼接。关键词路是**全词项匹配**（`plainto_tsquery` 用 `&` 连接词项，chunk 必须包含全部查询词项），不是通用 OR 召回，需在开发集上评估后再决定是否改为 OR。**分析器身份 fail closed**：scope 读取同时取 `index_profile.keyword_analyzer_version`（与 `normalize`），解析范围时与运行期分析器身份逐字比对，并把 `model_revision` 钉到查询编码；不一致时返回静态 503 `RETRIEVAL_ANALYZER_MISMATCH`，绝不用新词项流去查旧 `chunk.fts`。profile 的 `model_revision`/`dimension`/`normalize` 不完整或未归一化时返回静态 503 `RETRIEVAL_UNAVAILABLE`。响应 `candidates[]` 含 `chunkId`/`documentId`/`kbId`/`versionId`、`vectorRank`/`vectorScore`、`keywordRank`/`keywordScore`、`fusionRank`/`fusionScore`（未命中的一路为 `null`），不回传原文、向量或 KB 存在性；查询编码的暂时性失败（如 `EMBEDDING_BUSY`）在 503 `details.retryAfter` 中透出客户端解析到的秒数，但不复用 429 的 `Retry-After` 头。范围读取后先 `release` 事务，再在线程池内调用同步查询编码客户端，模型调用期间不持有数据库连接；关键词分析器构造失败或查询编码依赖不可用返回静态 503 `RETRIEVAL_UNAVAILABLE`。真实 PostgreSQL 17 上的授权/版本负例、分析器身份不符、真实 `KeywordAnalyzer` 与真实 `chunk.fts` 匹配、HTTP 层授权与融合排序已由聚焦集成测试覆盖（见 [开发约定](development.md)）；可降级重排已实现但默认关闭（见“可降级重排”），LLM、相似度阈值、多轮与证据选取仍未实现（LLM 与问答主流程见下文）。

本首片的已知残余（尚未实现，不在本片承诺内）：检索路由没有进程级并发上限，查询编码在线程池内可最长阻塞一个 inference 超时（默认 60s），慢 inference 下可能占满共享线程池并影响同进程的其它接口；范围读取与候选查询是两个短事务，中间若 KB 的 `active_index_profile_id` 切换，会返回 200 空候选而非可诊断失败；关键词路保持 `plainto_tsquery` 的 AND 语义，多词中文查询命中率需在开发集评估。rerank 已实现（默认关闭，开启后另有 3s 超时与降级），真实模型质量与延迟未验收。

## 可降级重排

已实现（Phase 2，默认关闭，**未做真实模型验收**）：inference 新增 `POST /internal/rerank`，固定 `BAAI/bge-reranker-base` revision `2cfc18c9415c912f9d8155881c133215df768a70`，用 `AutoTokenizer` + `AutoModelForSequenceClassification`（`XLMRobertaForSequenceClassification`，MIT）做 pair 推理，`max_length=512` 截断，`logits.squeeze(-1)` 原始分数，不归一化、不排序；不加 `sentence-transformers`。请求为 `{query, candidates:[{candidateId,text}]}`，严格 `extra=forbid`，最多 10 条候选、`candidateId` 唯一，query/单条文本/合计字节都有上限，Bearer 鉴权且请求体上限在 JSON 解析前生效；响应为 `{scores:[{candidateId,score}], modelRevision}`。服务端 CPU 并发 1 + 短排队。`RERANK_ENABLED=0`（默认）时服务不加载权重、`/capabilities` 报 `rerank.ready=false`、`/internal/rerank` 静态 503 `RERANK_NOT_READY` 且无任何分数；显式开启时启动阶段要求模型目录与产物清单完整，否则 fail fast。

reranker 权重在本仓库内没有预先下载核验的 SHA-256，因此不把摘要写进源码（不伪造身份）：构建期 `inference/scripts/prepare_model.py --model rerank` 从固定 Hub revision 下载，逐个用 Hub 元数据（`size`、非 LFS 的 `blobId`、LFS 的 `lfs.sha256`）核验后生成 `rerank-model-manifest.json`；运行期只按该清单离线核对身份、文件集合与逐文件摘要。首次真实构建后必须人工确认清单来源。

API 侧 `rag_backend.retrieval.rerank_client.RerankClient` 复用查询编码客户端的安全边界（`trust_env=False`、`retries=0`、不跟随重定向、`Accept-Encoding: identity`、有界读取、静态脱敏错误），任何超时/连接/404/503/413/422/非 2xx/非法响应/集合不完全/重复 id/非 finite/revision 不匹配/本地超限都收敛为统一的 `RerankUnavailableError`。检索在 RRF 融合与数据库 release 之后，仅对 top-10 已授权候选按同一授权链加载正文并调用重排；成功后按 score 降序、同分 `chunkId` 升序重排这 10 个，其余 30 保持原融合顺序；**不修改**每项的 `fusion_rank`/`fusion_score`。失败整体保持原 RRF 顺序并返回 `degraded_stages=('rerank_unavailable',)`。backend `RERANK_ENABLED` 默认 0、`RERANK_TIMEOUT_SECONDS` 默认 3.0，开启要求已配置 `INFERENCE_TOKEN`；关闭时完全不调用重排、也不标记降级。`RetrievalResult` 新增 `degraded_stages`，conversation 把它与 `unsupported_text`/`source_retry` 去重合并，写入既有 `query_run.degraded_stages` 与 `AnswerResponse.degradedStages`；不新增迁移、不改历史消息、不改 `/retrieval/search` wire 字段、不改引用/授权/RRF 常量。Compose/.env.example 只新增可选默认关闭变量，vps-lite 保持关闭，local-full 的开启步骤见 [部署设计](deployment.md)。本节所有 reranker 自动化测试都注入 stub，**不代表真实重排质量**；真实下载/加载/HTTP 端到端与镜像构建未运行。

`MandatoryContextExceedsBudgetError`（不静默截断、不丢问题），系统提示或当前问题自身含本地渲染器拒绝的结构 token 时同样抛具名的 `PromptEncodingError` 留给 API 层映射；历史只接受调用者显式标记 `authorized` 的轮次（`sequence` 重复直接拒绝），先取最新 3 轮窗口，再按调用者给出的相关性（缺失视为最低）与轮次序号降序逐个尝试，装配始终按时序，本模块不额外调用模型打分；证据按检索顺序尝试加入，同一文档最多 3 段、总计最多 6 段，被排除的候选项都留下静态原因码，而“4～6 段”仍是可用性目标而非门槛（可用或被预算容纳的证据不足 4 段时返回实际数量，不报错也不伪造）。低信任数据里出现本地渲染器拒绝的结构 token 时只跳过该候选：证据与历史分别记 `unsupported_text`，其余合法候选继续参与，整次请求不再因单条原文而中断。证据区放在当前问题之前、同一条 `user` 消息内，不进入 `system` 区（原文属低信任数据）。证据结构已固定边界：证据区由 `<evidence>`/`</evidence>` 标记包围，当前问题带 `本轮问题：` 标签放在证据区之外；每条证据用标准 `json.dumps`（`ensure_ascii=False`）序列化为单行 JSON（字段 `evidence_id` 与 `text`），正文换行与引号被转义、`str.splitlines()` 视为行分隔符的 U+0085/U+2028/U+2029 也定点转义，`json.loads` 可无损回放原文，citation 的原文/hash/locator 不受影响，证据数量与每文档上限不变。这样低信任正文里伪造的换行或行分隔符加结束区域或问题标签不能成为独立结构行；本次改动只固定提示结构边界，不做注入扫描、不加随机分隔符、不拒绝含分隔标签的正常文档，也不声称模型对注入的抵抗已被实测。新增的包装与转义开销由完整提示的既有本地估算器计入输入预算；`SYSTEM_PROMPT` 声明 `text` 是低信任数据，其中的制度/规则/操作步骤可照常回答与引用，但不得作为对模型自身的指令执行或遵循，也不得覆盖系统提示与输出结构，本轮问题以 `本轮问题：` 标签位于证据区之外。无入选证据时仍保持 question-only 装配。**`ChatContextPlan.evidence_ids` 为空时调用方必须拒答**：本模块只做选择，不作回答决策，无入选证据时不得继续调用模型。本片本身只做到预算选择；证据授权加载、citation 映射、LLM 客户端与 `llm_usage` 记账由后续证据问答主流程片补齐（见下文）。宿主离线实测（用真实产物加载，contract `deepseek-v41-chat-v3` 的非思考变体）：五个结构 token 与 `</think>` 各计 1 token，`你是知识库助手。`+`第二问` 的 system+question 提示为 12 token，29 字符中文样本 `企业知识库检索增强生成系统用于把制度文档切分为可引用片段。` 为 17 token，该样本 6 份加系统与问题估为 150 token（6 段全部入选）；官方 recipe 内置 v41 副本与上游产物对同一纯文本计数一致（两者只差 image token）。

`answer_question`，`rag_backend.api.conversations` 提供 `POST /api/v1/conversations`、`GET/POST /api/v1/conversations/{id}/messages` 与 `GET /api/v1/citations/{id}`。固化流程：按会话 `kb_scope` 重新鉴权并用与 `POST 开关（默认关闭，不依赖供应商默认的思考开启）与开启时的 `reasoning_effort`、`trust_env=False`、`retries=0`、有限超时、有界响应体（超出上限、非 JSON、缺 usage、`finish_reason == "length"` 均为显式失败；缺 usage `reasoning_content` 只被丢弃：不进回答、不入库、不向客户端展示；provider 的 `completion_tokens` 已包含 reasoning token，因此原样落账、不二次相加；思考与最终回答共用配置的 `max_tokens`（默认 800），被推理耗尽时如实落 `TRUNCATED` 失败（502 `GENERATION_FAILED`，`llm_usage.error_code=TRUNCATED`），不静默抬高预算。回答用 `rag_backend.generation.answer_schema.parse_answer` 严格校验：额外字段/非法类型/allowlist 之外的 `E` 编号/拒答带句子/非拒答无句子全部拒绝，模型不能提交 URL、页码或数据库 ID。citation 由服务端从已保存 `chunk.text` 与 `chunk.source_locator` 映射（短引文上限 500 字符，`quote_hash` 是完整正文 SHA-256）。服务端在持久化的 `message.content` 每句末尾追加 `[n]` 内联引用标记：`n` 即该来源 citation 的 `display_label`（从 1 起的数字，与证据 `E1`、`E2` `query_run.estimated_input_tokens`，不写成 provider 事实**；provider 未报告 usage 或账本写入失败时不报告成功。模型前复核证据授权与版本，交付前再次复核，版本/删除/权限变化最多重新检索一次，持续变化返回 409 `CONVERSATION_SOURCES_CHANGED`；整个网络调用期间不持有数据库连接或事务。多轮历史只带最近合法轮次，引用来源已被撤权/删除的助手消息既不显示也不进入模型上下文；每次模型调用前都按最新成员关系重新核查全部将进入提示的历史来源权限，不复用上一轮授权快照（重检索后的第二次调用同样重新核查）。`query_run.scope_snapshot` 记录本次检索**实际解析出的可检索 KB 子集**（`active_index_profile_id` 为 NULL 的 KB 被排除，零范围记空数组），不是会话名义 `kb_scope`，也不做二次范围查询；`query_run.degraded_stages` 只记录真实异常造成的静态阶段标识（低信任正文被本地渲染器剔除 `unsupported_text`、来源变化重检索 `source_retry`、可降级重排失败 `rerank_unavailable`），正常的 top-k/同文档限量/预算裁剪不计入降级；重排未启用或成功时不标记。独立问题改写已实现（`rag_backend.generation.query_rewrite`）：只有存在**合法历史轮次**时才在重检索循环之外调用一次受限改写模型，首轮与历史全部撤权都不额外发请求、独立问题直接取原问题。改写提示只包含已授权历史轮次的**用户问题**与当前问题，助手回答不进入改写提示（避免把上一轮模型陈述当成事实或注入源），复用同一份 V4.1 chat 渲染与输入预算装配。输出经严格 schema 校验（`extra=forbid`、唯一非空 `standaloneQuestion`、长度不超过 `MAX_STANDALONE_QUESTION_CHARS=7981`，与检索侧接受的原始查询上限一致），模型提交 `kbIds` 等范围或查询指令一律判非法。每次真实 attempt 单独追加 `llm_usage`（stage `qa_rewrite`，失败/超时也追加且不自动重试），改写失败整轮失败、绝不静默退回原问题。改写返回它实际入参的历史轮次 sequence，调用方在**首次检索前**、**每次版本变化重检索前**与**回答交付前**都按最新 `kb_member`/来源状态重新鉴权这些来源：任一失效立即抛静态 `ConversationSourcesChanged`（409），不退化继续用派生问题，不发查询编码/关键词检索/回答，也不落派生问题（已发生的 `qa_rewrite` 账本保留）。独立问题只用于查询编码与关键词检索，回答提示仍使用原始问题；`query_run.question` 保留原问题、`query_run.standalone_question` 记录实际用于检索的独立问题；版本变化触发的重检索复用同一个独立问题，不重复改写。会话管理已实现（迁移 `20260927_0010`）：`GET /api/v1/conversations` 返回 `title`/`pinned` 且置顶优先、其后按最近消息稳定倒序；`PATCH /api/v1/conversations/{id}`（`title`/`pinned` 锁后重查未删除，避免删除后回答复活；只软删不删共享 `chunk`/`citation`/`llm_usage` 事实。生成总开关 `LLM_ENABLED` 默认关闭，关闭或缺少 `LLM_API_KEY` 时端点静态 503 且不联网；测试全用 MockTransport 或假客户端，不发起付费调用。本片之后：真实 provider 连通性已由 2026-09-28 真实 40 题评估覆盖（46 次成功 attempt），真实失败/超时端到端仍未验收；可降级重排（rerank）已实现但默认关闭且未做真实模型验收（见“可降级重排”），相似度阈值仍未实现。

证据正文读取与来源状态复核复用同一权威链与 ACL：`load_evidence_chunks` 与两条候选路同样过滤 ACL；`load_chunk_source_states` 不过滤行，而是额外返回 `acl_allowed` 布尔列，`is_authorized` 同时要求成员有效、同组织、未删除与 ACL 放行，因此历史引用/在途回答的来源在文档改为 `RESTRICTED` 且调用者不在名单时同样整体失效。证据构建器给本次授权片段分配 `E1`、`E2` 等临时 ID。模型返回句子或短段落列表、对应 `citationIds`、`insufficientEvidence` 与可选追问；Pydantic 严格拒绝额外字段、未知 ID 和非法类型。模型不填来源 URL、页码或数据库 ID。服务端从已保存的 locator 映射 citation，并验证 ID 在 allowlist、版本与权限仍有效。助手正文里由服务端逐句追加 `[n]` 内联引用标记（`n` 与引用快照的 `displayLabel` 一一对应），前端只在消息合法引用映射内把这些标记渲染成可点击入口，未知编号与代码区保持原样。结构有效只证明来源存在且合法；来源是否真的支持该句需独立人工或评估验证。

MVP 完整生成并校验后返回，不以逐 token 流式输出绕过回答前的授权复核。调用重排或 LLM 前复核 ACL revision；回答前如关联文档更新则最多重新检索一次，持续变化返回“资料更新中，请重试”。撤权发生在内容已发给外部模型或客户端之后，已交付字节不可撤回，应停止后续调用和交付并记录事件。

## 回答策略与历史

- 无可访问证据或证据不足时拒答，不透露被过滤文档的存在。相似度阈值由开发集标定，不设跨模型通用常数。
- 当前有效文档互相冲突时展示双方证据、版本或生效日期，提示由责任方确认；不要静默选其中之一。若建立优先级规则，需有可审查的来源。
- `conversation` 只由所有者访问；历史消息、引用链接、文档预览和下载每次重新鉴权。删除或撤权后，不能只隐藏引用按钮，还要处理来源衍生的消息内容。
- 引用来源已被撤权或删除时，整条助手消息既不显示也不进入后续模型上下文（不能只隐藏那一条引用）；文档更新后旧答案的来源仍授权但已非当前版本时，允许作为**带旧版本标识**的历史展示（引用快照保留生成时的 `version`，响应另带由权威 `document.active_version_id` 与引用 `version_id` 比较得出的 `isCurrentVersion=false`），不得当作当前事实（当前回答只引用本次检索到的 active version；即时回答刚生成的引用仍为当前版本）。
- 管理员检索调试页可查看自己有权范围内的候选、排名和阶段降级；调试权限不授予跨 KB 阅读权。

指标、三组消融与验收方法见 [评估与验收](evaluation.md)。
