# API 契约草案

> OpenAPI 已由 FastAPI 生成；`GET /health`、认证组 `POST /auth/login`、`POST /auth/logout`、`GET /me`、知识库组 `GET /knowledge-bases`、`POST /knowledge-bases`、`GET /knowledge-bases/{id}/members`、`PUT /knowledge-bases/{id}/members`、文档上传 `POST /knowledge-bases/{id}/documents`、文档列表 `GET /knowledge-bases/{id}/documents`、文档详情 `GET /documents/{id}`、文档新版本 `POST /documents/{id}/versions`、逻辑删除 `DELETE /documents/{id}`、授权检索 `POST /retrieval/search` 与问答组 `POST /conversations`、会话列表 `GET /conversations`、会话改名/置顶 `PATCH /conversations/{id}`、逻辑删除 `DELETE /conversations/{id}`、`GET /conversations/{id}/messages`、`POST /conversations/{id}/messages`、引用详情 `GET /citations/{id}` 已实现，其余接口与标为“后续”的接口仍未实现。外部统一前缀 `/api/v1`。MVP 范围见 [交付计划](roadmap.md)；标为“后续”的接口不属于 MVP。

Session Cookie 使用 HttpOnly、SameSite，并在生产环境启用 HTTPS；状态变更接受 CSRF 防护。请求/响应由 Pydantic 定义，外部字段使用 camelCase。标准错误体含 `code`、`message`、`requestId`、`details`，无权资源使用不暴露存在性的统一策略。异步入库、重建和评估受理后返回 `202`，不代表任务完成。

已实现的认证接口：`POST /api/v1/auth/login` 请求体为 `{"username":"...","password":"..."}`，先校验 `Origin` 白名单再进行 Redis 登录限流，成功后返回 `{"user":{"id","username","isAdmin","organizationId"},"csrfToken","generation"}` 并在 `Set-Cookie` 写入 HttpOnly + SameSite=Lax 会话 Cookie（生产默认 Secure，本地回环可显式关闭）；`generation` 是只读生成能力事实 `{"enabled","defaultModel","defaultThinking","models":[{"id","thinking":{"supported","efforts","defaultEffort"}}]}`，只列举服务端已验证、且与固定 tokenizer/渲染契约兼容的模型（当前仅 `deepseek-flash`，思考强度 `low`/`high`/`max`，省略请求字段时的默认组合是 `defaultModel` + `defaultThinking=disabled`）；未验证的官方模型（如 `deepseek-v4-pro`）既不接受也不展示。限流的客户端 IP 在可信代理网段内取网关覆盖的 `X-Real-IP`，否则取直连对端地址。未知用户、禁用与密码错误统一返回 401 `AUTH_INVALID_CREDENTIALS`，不泄露用户名是否存在；超过限流阈值返回 429 `AUTH_RATE_LIMITED` 与 `Retry-After`；Redis 不可用返回 503 `AUTH_DEPENDENCY_UNAVAILABLE`。`POST /api/v1/auth/logout` 要求 `X-CSRF-Token`，软撤销服务端会话并在确实撤销后才清除 Cookie，无有效会话时幂等返回 204 且不下发 `Set-Cookie`。`GET /api/v1/me` 每次从数据库重建授权上下文，会话撤销、到期或用户禁用立即返回 401；CSRF 令牌由服务端密钥派生，因此在进程重启后仍能从会话恢复同一 `csrfToken`；`GET /me` 还返回当前可访问 KB 的 `knowledgeBases` 角色概览（`[{id,name,role}]`）与同一份只读 `generation`。422 校验错误体的 `details` 只含 `type`/`loc`/`msg`，不回显请求输入（包括密码）。

已实现的 KB 成员接口：`GET /api/v1/knowledge-bases` 只返回当前用户在服务端会话组织内仍是有效成员的 KB（`{"knowledgeBases":[{id,name,role,aclRevision}]}`），组织与角色都来自数据库 `kb_member`，`organizationId` 不在请求体中定义，即使提交也不生效。`POST /api/v1/knowledge-bases` 请求体只有 `{"name"}`，要求管理员（`user_account.is_admin`）、合法 `Origin` 与 `X-CSRF-Token`，并在同一事务创建 KB 与创建者的 `OWNER` 成员行，成功返回 201 `{id,name,role,aclRevision,kbRevision}`。`GET /api/v1/knowledge-bases/{id}/members` 允许同组织任意有效成员读取，返回 `{members:[{userId,username,role}],aclRevision}`。`PUT /api/v1/knowledge-bases/{id}/members` 只允许 `OWNER`、合法 `Origin` 与 CSRF，请求体 `{members:[{userId,role}]}` 做全量替换：缺席者软撤销、重加入者清空 `revoked_at` 并更新角色；空列表与重复用户返回 422 `KB_MEMBERS_INVALID`，引用不存在或外组织用户返回 422 `KB_MEMBER_USER_INVALID`，新加入或提升已禁用用户为 `OWNER` 返回 422 `KB_MEMBER_OWNER_DISABLED`，替换后没有任何 `OWNER`（或没有任何启用中的 `OWNER`）返回 409 `LAST_OWNER_REQUIRED`，被拒绝的请求不产生部分事务；只有实际变化才在事务内递增 `acl_revision`。KB 不存在、属于其他组织、成员已撤销或角色不足统一返回不暴露存在性的 404 `KNOWLEDGE_BASE_NOT_FOUND`；成员替换在事务内锁定知识库行以序列化并发，在锁内复核调用者仍是该 KB 的有效 OWNER，并在同一事务内读出成员快照，使响应体与 `aclRevision` 一致。本切片没有用户目录或用户查询接口，成员替换请求体里的 `userId` 只能取自运维开户 CLI 打印的账号 id，不能用用户名代替。本切片不提供管理员接管或自动恢复：成员替换要求至少一名启用中的 OWNER，这是事务时点校验而非数据库永久约束；若唯一 OWNER 已被直接写库禁用，现有 API 无法把所有权移交给无法登录的账号，只能由运维先在数据库层把该账号 `enabled` 恢复，再由本人登录移交。

已实现的 Markdown 上传接口：`POST /api/v1/knowledge-bases/{id}/documents` 为 multipart 请求（`title` 文本字段与 `file` 文件字段），必须携带 `Idempotency-Key` 请求头，并要求会话对该 KB 至少为 `EDITOR`、合法 `Origin` 与 `X-CSRF-Token`；授权、CSRF、Origin 与接收阶段体积上限都在调用 `request.form()` 之前完成，未授权请求不会把正文落盘。只接受 `.md`/`.markdown` 后缀且实际字节为有效 UTF-8、不含二进制控制字符的文本，或 `.pdf` 后缀且具备 `%PDF-` 魔数头的二进制原件（任何加密标志、结构损坏与页数超限由 worker 解析子进程静态失败，零可提取文本落 `NEEDS_OCR`）；`file` 最多 20,000,000 字节，`title` 最长 500 字符，`Idempotency-Key` 最长 255 字符。成功返回 202 `{documentId,versionId,jobId}`。同一 KB 下同一 `Idempotency-Key` 且内容与标题都相同时复用同一组 id（仍返回 202），命中已有 job 时一律不会自动处理：即使该 job 已被接收壳静态拒绝为 `FAILED`+`LEGACY_JOB_UNSUPPORTED`，或它已有非 NULL 诊断码（如 `DELIVERY_UNCONFIRMED`）（已最终验收），202 都只表示受理、不是处理进度或成功，也不会重新解析或复位，需要独立授权的人工恢复；内容或标题任一不同返回 409 `IDEMPOTENCY_KEY_REUSED`；不同 key 即便内容相同也新建独立 document，换全新 `Idempotency-Key` 会生成带默认 profile 与真实 parser 的新 job，但这不是对旧 job 的自动恢复，且若旧内容 blob 已存在，是否已有旧相同 blob 及其业务影响需按权限处理、不是自动修复。去重键在服务端以组织+KB+规范化 key 的 SHA-256 存储，错误体不回显 key 原值、文件内容或文件名。错误映射：超过 20,000,000 字节 413 `DOCUMENT_TOO_LARGE`，空内容 422 `DOCUMENT_EMPTY`，非 UTF-8 或含二进制控制字符 422 `DOCUMENT_NOT_TEXT`，`.pdf` 内容缺少 PDF 魔数头 422 `DOCUMENT_NOT_PDF`，非常规文本后缀 422 `UNSUPPORTED_DOCUMENT_TYPE`，标题非法 422 `DOCUMENT_TITLE_INVALID`，key 非法 422 `IDEMPOTENCY_KEY_INVALID`，缺少 `Idempotency-Key` 请求头 422 `VALIDATION_ERROR`，multipart 格式错误 422 `UPLOAD_MALFORMED`。本切片只受理并持久化入库事实：document `CREATED`、version `PENDING`（新上传登记真实解析器版本 `markdown-it-py-4.2.0-v1`，既有版本行与幂等回放保持占位 `markdown-v1`、不自动升级；上传事务不解析正文；该新版行为已由独立 tester 在隔离 PostgreSQL 17 + Redis 上验收：`tests/integration/test_document_upload_flow.py` 11 passed/0 skipped，且旧 `markdown-v1` 行的幂等回放后版本保持占位）、job `QUEUED`（新上传先在 IO 线程按需预热 jieba 身份，失败即 fail-closed；随后在 publish 前只读预检同 `config_hash` 既有行（`precheck_default_index_profile`，字段不一致 fail closed、不发布 blob）；再在同一个四表事务内 `ensure_default_index_profile(session)` 登记/复用默认全局 index profile 并把其行 id 显式写入 `ingest_job.profile_id`；幂等回放既有任务不改写其 已实现的文档新版本与逻辑删除接口：`POST /api/v1/documents/{document_id}/versions` 为 multipart 请求（`title`、`expectedVersionId` 文本字段与 `file` 文件字段），必须携带 `Idempotency-Key`，要求会话对该文档所属 KB 至少为 `EDITOR`、合法 `Origin` 与 `X-CSRF-Token`；`expectedVersionId` 必须是当前 `document.active_version_id`，过期返回 409 `DOCUMENT_VERSION_CONFLICT`。去重键在服务端以组织+KB+文档+规范化 key 派生（命名空间前缀 `ver1:`，与首次上传的裸 SHA-256 键互不匹配），命中时校验文档未删除、`expectedVersionId`、内容摘要与标题；**标题身份取受理时固化的 `ingest_job.request_title`**（迁移 `20260926_0008` 新增；旧 NULL 行回退到当前 `document.title`），不再依赖会随新版本切换的展示标题，因此改标题后原 key 仍能原样重放；同键同 expected 的有效回放返回同一新版本（仍 202），任一不同返回 409 `IDEMPOTENCY_KEY_REUSED`。`version_no` 在 `document` 行锁内取 `max+1`，同一文档的并发新版本因行锁串行化，同键并发只产生一个版本。受理后 `document.active_version_id` 不变，旧版本继续 READY 可检索；只有发布事务在行锁内 compare expected active 且未删除后才切换指针，旧版本无需退役但不再参与检索（检索按 `active_version_id` 过滤），失败只把新版本置 `FAILED`、绝不下线旧版本；陈旧 expected 若在领取期即可确认（已被更早发布超越）则静态失败为 `PIPELINE_STALE_EXPECTED`。`DELETE /api/v1/documents/{document_id}` 要求该 KB `OWNER`、合法 `Origin` 与 CSRF，在 `document` 行锁内置 `deleted_at`/`lifecycle_status=DELETED` 并递增 `kb_revision`，把该文档所有非终态 `ingest_job`（排队与处理中）置 `CANCELLED` 并清租约；成功与二次删除都返回 204（幂等）。删除锁序与 worker 相反时可能与失败/发布事务死锁（SQLSTATE `40P01`），服务端在完整事务回滚后有限重试并**重新授权**，成功只提交一次、无重复副作用；即使 job 保留租约，发布事务也先按 `deleted_at` 拒绝且不复活文档。只做逻辑 tombstone，保留共享 blob/版本/索引历史，**不**返回 `cleanupJobId`、不做物理回收；已删除文档的旧幂等上传回放返回 409 `DOCUMENT_DELETED`，不得当有效新资源。本切片由 `tests/integration/test_document_update_delete_flow.py` 在隔离 PostgreSQL 17 + Redis 上验收（11 passed，见 [开发约定](development.md)）。

已实现的个人 RAG 读取接口：`GET /api/v1/knowledge-bases/{id}/documents` 与 `GET /api/v1/documents/{document_id}` 要求会话对该文档所属 KB 至少 `READER`（复用 `require_kb_role`/`require_document_role`，每次从数据库 `kb_member` 重建），KB 不存在、跨组织、成员已撤销、文档不存在或已删除都统一返回不暴露存在性的 404（列表/详情分别为 `KNOWLEDGE_BASE_NOT_FOUND`/`DOCUMENT_NOT_FOUND`）。两者排除逻辑 tombstone 的文档（`deleted_at` 非空或 `lifecycle_status='DELETED'`），并按 `organization_id` 与 `knowledge_base` 同组织过滤。文档对象字段固定为 `{id,title,sourceType,lifecycleStatus,activeVersion,latestVersion,latestJob,createdAt,updatedAt}`：`activeVersion` 为 `document.active_version_id` 指向的版本或 `null`，`latestVersion` 取 `version_no` 最大的版本或 `null`，`latestJob` 只属于 `latestVersion` 并按 `(created_at,id)` 稳定取最新或 `null`，因此能在新版本入库中同时展示仍服务的旧 `activeVersion` 与 `latestVersion`，也能原样暴露 `NEEDS_OCR`；三者只含 `{id,versionNo,status}` / `{id,status,errorCode}`，不返回 `file_ref`/`file_hash`/租约或任何正文。`GET /api/v1/conversations` 只按所有者隔离（`owner_id` + `organization_id`），返回 `{conversations:[{id,title,pinned,kbIds,createdAt,lastMessageAt}]}`：`title` 为首轮提问派生的展示标题（尚无标题为 `null`）、`pinned` 由服务端 `pinned_at` 非空派生，`kbIds` 取自会话固化的 `kb_scope`，`lastMessageAt` 为最近消息时间（无消息为 `null`）；已软删会话不出现；排序为置顶优先，其后按最近消息时间（无消息回退创建时间）稳定倒序。列表用单次带相关子查询的聚合读取，不读取消息正文，也不产生 N+1。上述三个接口在个人规模下**明确不分页**，不新增索引/迁移/泛查询框架；本切片新增聚焦单元测试 `tests/unit/test_document_read.py` 与 `tests/unit/test_conversation_list.py`（纯装配 + 进程内 HTTP 契约 + 编译语句静态检查，未在真实 PostgreSQL 上验收）。

已实现的检索接口：`POST /api/v1/retrieval/search` 请求体为 `{"query":"...","kbIds":["..."]}`，要求有效会话（对该 KB 至少 READER）；`query` 最长 7981 字符（对齐查询编码客户端对完整模型输入的实际限制），`kbIds` 必须非空且是会话可访问 KB 集合的子集，否则统一返回不暴露存在性的 404 `KNOWLEDGE_BASE_NOT_FOUND`；空/纯空白/超长 `query` 与空 `kbIds` 由请求 schema 返回 422 `VALIDATION_ERROR`，仅当分词或查询编码客户端在本地校验阶段拒绝查询时，才作为兜底返回 422 `RETRIEVAL_QUERY_INVALID`。`active_index_profile_id` 为 NULL 的 KB 不参与检索；请求范围跨越多个不同 active profile 返回 422 `RETRIEVAL_PROFILE_CONFLICT`；profile 的 `keyword_analyzer_version` 与运行期分析器身份不一致时返回 503 `RETRIEVAL_ANALYZER_MISMATCH`。服务端用同一授权 JOIN 跑 pgvector exact 向量路与 `plainto_tsquery('simple', :terms)` 关键词路各 top-20（关键词路是全词项匹配），再以 RRF（k=60、按 `chunkId` 去重、最多 40）融合；成功返回 200 `{"candidates":[{chunkId,documentId,kbId,versionId,vectorRank,vectorScore,keywordRank,keywordScore,fusionRank,fusionScore}]}`，未命中的一路字段为 `null`，不回传原文、向量或 KB 名称。查询编码依赖不可用或关键词分析器不可用返回静态 503 `RETRIEVAL_UNAVAILABLE`；查询编码的暂时性失败（如 `EMBEDDING_BUSY`）在 503 `details.retryAfter` 返回客户端解析到的重试秒数。本接口只检索，不含重排、生成回答与相似度阈值；`POST /retrieval/debug`、多轮问答与引用仍未实现。授权、版本、profile 与分析器身份过滤均在两条 SQL / 范围解析内，且查询编码期间不持有数据库连接；真实 PostgreSQL 17 的聚焦集成验收见 [开发约定](development.md)。

已实现的问答接口：`POST /api/v1/conversations` 请求体只有 `{"kbIds":[...]}`，要求会话对该 KB 至少 `READER` 且要求合法 `Origin` 与 `X-CSRF-Token`，在单个事务内创建所有者会话并把 KB 集合固化为 `kb_scope`（独立问题改写只能收窄、不能扩大该范围），成功返回 201 `{conversationId,kbIds,createdAt}`。`POST /api/v1/conversations/{id}/messages` 请求体为 `{"question":"...","requestId":"...","model":"...","thinking":{"type":"enabled|disabled"},"reasoningEffort":"low|high|max"}`，除 `question` 外全部可选，且请求体禁止未知字段（`extra=forbid`，客户端不能提交 endpoint 或任意模型））：`question` 最长 8000 字符且非空白；`requestId` 最长 128 字符，本片只作为关联标识记录在 `query_run`，不实现按它去重；省略 `model`/`thinking`/`reasoningEffort` 等价于默认模型 + 关闭思考，与旧请求体逐字兼容。`model` 只接受服务端已验证白名单（当前仅 `deepseek-flash`），提交未验证模型返回 422 `GENERATION_OPTION_UNSUPPORTED`；`reasoningEffort` 只在 `thinking.type=enabled` 时合法，未知取值或关闭思考时提交强度由 schema 返回 422 `VALIDATION_ERROR`。仅会话所有者可写并要求合法 `Origin` 与 404，删除后列表、历史、引用与追加追问全部拒绝；追加追问在提交写入前会再次检查会话未删除，避免在生成期间被删除后把回答复活成新消息。本片不实现恢复已删除会话、分页与批量操作。本片不实现重排降级标记；真实 provider 连通性已由 2026-09-28 真实 40 题评估覆盖，真实失败/超时验收仍未做。追问改写已实现：`query_run.question`
