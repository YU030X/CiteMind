## 身份和授权

已完成 Phase 1 身份首片：账号由运维 CLI `uv run python -m rag_backend.auth.cli` 显式创建（默认隐藏输入密码；自动化用 `--password-env`/`--password-file`/`--password-stdin`，明文与哈希都不打印），密码用 Argon2 哈希。CLI 拒绝 `--organization-id` 与 `ORGANIZATION_ID` 不一致的开户请求（返回非零且不建号），登录只按 `ORGANIZATION_ID` 查账号；建号前以只读 `SELECT current_user` 预检连接角色，非 `citemind_api` 时显式失败且不写入。单组织配置改变后，属于旧组织的既有会话在下次请求即返回 401（`build_auth_context` 校验 `user_account.organization_id` 与配置一致）。登录 `POST /api/v1/auth/login` 先校验 `Origin` 白名单，再在 Redis 中按客户端 IP 与用户名原子限流，通过后签发 256-bit 随机会话令牌。Cookie 为 HttpOnly + SameSite=Lax，生产默认 `Secure`，只在非生产的回环来源可用 `SESSION_COOKIE_SECURE=0` 显式关闭。数据库 `auth_session` 只保存 token hash、CSRF token hash、到期与撤销状态；CSRF 令牌由服务端 `CSRF_SECRET` 与会话令牌 HMAC 派生，因此 `GET /me` 可在进程重启后恢复同一 CSRF 令牌，而不保存原令牌。每次 `GET /me` 都从数据库重建授权上下文；注销、到期、禁用与撤销立即返回 401，权限结果不跨请求缓存。限流 Redis 不可用时登录返回 503（fail closed），未知用户、禁用与密码错误统一返回 401 并执行等价的 Argon2 计算。状态变更请求（注销、创建 KB、替换成员）要求 `X-CSRF-Token`；迁移 `20260923_0005` 的 api 角色只有 `user_account`/`auth_session`/`kb_member` 的 SELECT+INSERT+UPDATE，撤销走软删除，运行角色没有 DELETE 权限。`auth_session` 目前也没有清理作业，已撤销与已过期会话行会一直保留；清理期限与负责作业尚未实现，这是剩余保留风险和未来维护责任，本切片不声明任何已实施的清理策略。登录限流的客户端 IP 只信任显式配置的可信代理网段（`TRUSTED_PROXY_CIDRS`）：只有当直连对端落在该网段内时，才接受网关用 `$remote_addr` 覆盖的单值 `X-Real-IP`；否则退回对端地址，且从不读取可被追加伪造的 `X-Forwarded-For`；生产环境必须显式配置该边界，并拒绝 `0.0.0.0/0` 与 `::/0` 这类全网段（信任全网段等于取消对端校验），更窄的宽网段仍由运维按网络拓扑判断；生产环境 `ALLOWED_ORIGINS` 必须全部使用 https。注销只在服务端会话确实被撤销后才下发清除 Cookie，无有效会话的请求不下发 Set-Cookie。

KB 成员授权的服务端判定已实现：`require_kb_role` 每次请求都从数据库 `kb_member` join `knowledge_base` 重新判定当前用户在指定 KB 的最小角色（READER<EDITOR<OWNER），不跨请求缓存；KB 不存在、属于其他组织、成员已撤销或角色不足统一返回不暴露存在性的 404 `KNOWLEDGE_BASE_NOT_FOUND`。`GET /knowledge-bases` 只列会话组织内有效成员 KB；`POST /knowledge-bases` 只允许 `user_account.is_admin`，强制 Origin 与 CSRF，并在同一事务写入创建者 OWNER；`PUT /knowledge-bases/{id}/members` 只允许 OWNER，强制 Origin 与 CSRF，做全量替换：缺席者软撤销、重加入者清空 `revoked_at`，空、重复、缺少 OWNER 或引用外组织用户都拒绝且无部分事务，事务内锁定知识库行序列化并发并在锁内复核调用者仍是 OWNER，只有实际变化才递增 `acl_revision`。请求体中 `organizationId` 不生效（即使提交也不被采用），角色与用户组织都由服务端核对。替换结果必须至少保留一名启用中的 OWNER：新加入或提升一名已禁用用户为 OWNER 会被拒绝（422 `KB_MEMBER_OWNER_DISABLED`），只保留已禁用 OWNER 而不搭配任何启用 OWNER 则返回 409 `LAST_OWNER_REQUIRED`。该约束是替换事务时点的应用校验，数据库没有对应的永久约束，直接写库禁用最后一个 OWNER 或把唯一 OWNER 指向已禁用用户会绕过它。禁用 `user_account` 不会软撤销其 `kb_member` 行：成员记录保留，成员列表可能包含已禁用用户，账号重新启用后原角色恢复。正确的顺序是在禁用账号前先完成所有权移交；如果唯一 OWNER 已被直接写库禁用，现有 API 无法把所有权移交给一个无法登录的已禁用账号，本切片也没有管理员接管或自动恢复能力（当前没有 CLI 恢复/禁用入口），只能由运维在数据库层把该账号重新置为 `enabled` 后，再由本人登录完成移交。知识库角色为 OWNER、EDITOR、READER：READER 可问答和查看可见原文，EDITOR 可导入/更新，OWNER 可管理成员与删除。MVP 以 KB 成员授权；文档 ACL（已实现）只能进一步收紧，不能放宽 KB 成员读权限。读规则为当前组织、KB 成员、满足文档允许列表（若存在）、未删除、当前有效索引；组织和成员身份都来自后端会话。客户端 `kbIds` 只能取交集。

文档新版本与删除的授权已实现：`require_document_role` 每次请求把路径 `document_id` 解析到其 KB 的有效未撤销 `kb_member` 角色，不跨请求缓存；文档不存在、跨组织、成员已撤销或角色不足统一返回 404 `DOCUMENT_NOT_FOUND`，不泄露文档存在性。更新要求至少 `EDITOR`、删除要求 `OWNER`，两者都强制 Origin 与 CSRF。该解析**不过滤** `deleted_at`，因此已删除文档对有权限的调用方得到确定状态（更新/旧回放返回 409 `DOCUMENT_DELETED`、删除返回幂等 204），对无权限者仍为 404。幂等身份不再依赖可变的展示标题：标题取受理时固化的 `ingest_job.request_title`（迁移 `20260926_0008`，旧 NULL 行才回退 `document.title`），因此新版本切换 `document.title` 不会让原 key 的原样重放变成 409，而同一 key + 不同标题仍为 409。新版本去重键只落 SHA-256 摘要（含 `document_id` 与 expected active），不落 `Idempotency-Key` 原值或文件名，错误体也不回显它们。删除在 `document` 行锁内完成，取消该文档非终态 `ingest_job` 时同时清空租约，使在途 worker 失去发布资格；删除锁序与 worker 相反可致死锁（`40P01`），服务端在完整事务回滚后有限重试并每次**重新授权**（不复用死锁事务中的角色快照），成功只提交一次。本切片当时不删除共享 blob、不新增 DELETE 授权、不做物理回收；其后的文档 ACL 切片首次给 `citemind_api` 授予 `document_acl` 的 DELETE（全量替换名单），仍然不删除业务文档、blob 或向量。

文档读取收紧与原文下载已实现（迁移 `20260928_0012`、`document.acl_mode` 与 `document_acl`）：`require_document_read` 每次请求从数据库解析「文档 → KB → kb_member」并叠加 ACL：文档未删除、同组织、成员未撤销，且 `acl_mode='INHERIT'` 或用户在 `document_acl` 中登记为 `USER`/`READ`。`RESTRICTED` 空名单连 OWNER 也不能读，管理权（KB `EDITOR` 更新、`OWNER` 删除与管理 ACL）不受影响。`PUT /documents/{id}/acl` 只允许 OWNER、强制 Origin 与 CSRF，全量替换（先删后插），`INHERIT` 携带名单或重复用户返回 422 `DOCUMENT_ACL_INVALID`，引用不存在/跨组织/已禁用/非本 KB 成员返回 422 `DOCUMENT_ACL_MEMBER_INVALID`，文档不存在/已删除/越权统一 404；只有模式或名单实际变化才在事务内递增 `knowledge_base.acl_revision`，重复替换幂等。替换锁序与删除一致（`document` 行锁 → `knowledge_base` 行锁 → `document_acl` 写入），并在锁内复核调用者仍是 OWNER、不锁定 `kb_member`，避免与成员替换（`knowledge_base → kb_member`）形成新环。`GET /documents/{id}/content?versionId=` 默认交付 active、显式版本必须同文档且合法；跨文档/跨组织/未授权/已删除统一 404；服务端在 IO 线程内用 `DocumentBlobStore.read_verified_blob` 校验 `file_ref`/摘要/20,000,000 字节并返回原始字节，IO 前与交付前各重核一次授权：读取期间默认 active 变化返回 409，撤权/删除返回 404；响应为 `no-store` + `nosniff` + `attachment`，MIME 只从受控来源映射，失败（含 blob 损坏）返回不含路径的静态 500。管理权不等于读权，且已发字节无法追回。

index profile 的登记入口 `ensure_default_index_profile` 只使用 `citemind_api` 对 `index_profile` 的 SELECT 与 INSERT：不可变契约由「不授予 UPDATE」强制，运行角色也没有 DELETE，worker 对该表只有 SELECT、无 INSERT；它不经任何业务 HTTP 入口暴露，客户端不能提交或选择 profile。该函数不 UPDATE `knowledge_base`、不回填 `active_index_profile_id`，不提交或回滚事务，并用 `session.no_autoflush` 抑制自动 flush。同模块的 `precheck_default_index_profile`（独立 tester 已在隔离 PostgreSQL 17 + Redis 上验收）在 publish 前只按默认契约 `config_hash` 做一次只读 SELECT 并逐项比对既有行，字段不一致 fail closed（新上传不发布 blob），它同样不写库、不 UPDATE KB、不 seed，但会开启只读事务并由调用方 rollback 释放。新 Markdown 上传写路径先调用只读预检，再在同一四表事务内调用 `ensure_default_index_profile` 把默认 profile 绑定到新 `ingest_job.profile_id`（独立 tester 已验收）；KB 创建与 worker 路径仍不调用，没有独立 seed、没有新迁移，dev 库 KB 的 `active_index_profile_id` 仍为 NULL（真实处理默认关闭、dev 未部署），登记全局 profile 不改变任何 KB 的授权或可检索性。

`ingest_job.profile_id` 迁移 `20260925_0006` 只增加一个可空外键，不为它单独授权：`citemind_api` 与 `citemind_worker` 对 `ingest_job` 的既有表级 UPDATE 授权本就覆盖该列，迁移不新增 `GRANT`/`REVOKE`。这意味着**数据库层面不保证 `profile_id` 不可变**——持有该表 UPDATE 的运行角色都能改写它，也不会自动核对它与目标 generation 的 profile 一致。新上传写路径已把默认 profile 写入新 `ingest_job.profile_id`（独立 tester 已验收），但数据库层面该列仍可被任何持有该表 UPDATE 的运行角色改写，未来 worker 接线必须在写入事务内限制对它的更改并在提交前核对 `generation.profile_id`；在实现与验收前不得声称 profile 绑定已冻结。该迁移不做 backfill/seed，旧 `QUEUED`/`HANDLER_NOT_READY` 行保持 NULL，不得被新 default profile 契约自动处理、补绑或重投；绑定不代表 profile 已 READY 或文档可检索。worker 接收壳现在读取 `ingest_job.profile_id`、`document_version.parser_version` 与 `error_code`，仅用于把无接收标记且 `error_code IS NULL` 的旧 job 静态拒绝为 `FAILED` + `LEGACY_JOB_UNSUPPORTED`，已有非 NULL 诊断码的旧 job 保持原样（已最终验收），不改写 `profile_id`，也不补绑或重投。

向量与关键词候选 SQL 复用同一授权 JOIN（首片已实现，见 [检索](retrieval.md)）：取候选时在两条 SQL 内过滤当前组织、未撤销 `kb_member`、未删除文档、`document.active_version_id`、`READY` generation、`kb.active_index_profile_id` 与一致的 `chunk_embedding.profile_id`，并以权威关系链而非 `chunk` 冗余列判定归属；关键词路还用该 profile 的 `keyword_analyzer_version` 与运行期分析器身份逐字比对（不一致 fail closed 静态 503），避免换词典后用新词项流查旧 `chunk.fts`；权限过滤不能拖到生成回答之后；reranker、LLM、日志和缓存也不得先收到越权内容。会话、检索调试、反馈、旧版本、引用和文件下载各自重新鉴权。证据问答主流程已实现：`POST /conversations`、`POST /conversations/{id}/messages`、`GET /conversations/{id}/messages`、`GET /citations/{id}`、`PATCH /conversations/{id}` 与 `DELETE /conversations/{id}` 全部按所有者隔离（会话不属于本人统一 404），写操作额外要求合法 `Origin` 与 `X-CSRF-Token`，每次追问和每次读取引用都从数据库重建 `kb_member` 状态；引用来源已撤权或删除时，历史中的助手消息整体隐藏、引用详情返回 404，且该助手消息不进入后续模型上下文。会话改名/置顶与逻辑删除要求的是**会话所有者**（不是 KB OWNER 角色），软删只写 `conversation.deleted_at`，不删共享 `chunk`/`citation`/`llm_usage` 事实；列表、单会话、历史、引用与追加追问全部过滤已删除会话，且追加追问在写入前重查未删除，避免在生成期间被删后复活回答。`GET /me`/登录响应的 `generation` 只读返回服务端配置的模型名与固定 `thinking=disabled`，不提供模型路由或思考强度切换入口，也不泄露密钥。撤权和删除先提交授权事实与 `acl_revision`/`kb_revision`，让后续访问立即失效，再做异步物理清理。权限查询 MVP 不跨请求缓存最终答案或授权结果。

## 输入与文件

Markdown/文本 PDF/DOCX 上传（`POST /api/v1/knowledge-bases/{id}/documents`）已实现输入校验与文件隔离：服务端在读取 multipart 正文之前先完成会话鉴权（对目标 KB 至少 `EDITOR`）、`Origin` 白名单与 `X-CSRF-Token` 校验，以及接收阶段的请求体字节上限；未授权请求不会把正文落盘。只按客户端字节判定，不信任声明的 MIME：后缀必须是 `.md`/`.markdown`（内容必须为有效 UTF-8 且不含二进制控制字符）、`.pdf`（内容必须带 `%PDF-` 魔数头）或 `.docx`（内容必须是以 `PK` 开头且标准库 ZIP 元数据符合收窄子集的 OPC 包），单文件最多 20,000,000 字节，空内容与伪装成文本的二进制都拒绝；PDF 的加密、结构损坏与超过 200 页由 worker 解析子进程静态失败（具名错误码，不静默生成空索引），零可提取文本落 `NEEDS_OCR`；DOCX 的嵌套表、`w:sdt`、`w:altChunk`/`w:customXml`、宏部件与实体声明等收窄外结构由 worker 解析子进程静态失败并落 `PIPELINE_DOCX_UNSUPPORTED`，坏 ZIP/CRC/XML 与实际解压总量超限落 `PIPELINE_DOCX_INVALID`；只索引 `word/document.xml` 正文，页眉、页脚、脚注、尾注、批注与文本框不索引。原文件由 API 写入 `api-documents` 命名卷，相对路径只由服务端 KB id 与内容 SHA-256 派生，不拼接用户文件名；Compose 中 worker 以同一 `DOCUMENT_STORAGE_DIRECTORY` 只读（`:ro`，uid 10001）挂载同一命名卷，inference 不挂载；写入先落同目录临时文件、`fsync` 后原子替换，失败只清理本次临时文件。`DocumentBlobStore.read_verified_markdown` 要求 `file_ref` 严格等于由 KB id 与摘要派生的路径（拒绝跨 KB、跨摘要或任意路径），打开前逐段 `lstat` 检查父目录与叶节点是否为符号链接或 Windows 联接点，可用时用 `O_NOFOLLOW` 打开并对已打开 fd `fstat`，只接受常规文件且不超过 20,000,000 字节，读取后核对内容摘要并复用上传侧 UTF-8/控制字节校验；PDF 经同一套严格二进制读取（`read_verified_blob`/`read_verified_pdf`，后者额外校验魔数），不做 UTF-8 解码；读失败一律为 `BlobReadError` 子类、非法 `file_ref` 为 `InvalidBlobReference`，错误信息静态且抑制底层含路径的 `OSError`。父目录 `lstat` 与 open 之间仍有 TOCTOU 窗口、联接点检查是尽力而为，本切片不声称已根除。当前 `worker.py` 尚未调用该读取器，合格 job 仍 `QUEUED`/`HANDLER_NOT_READY`、不读 blob；接收壳另有旧 job 静态拒绝路径（见上、已最终验收）会写 `error_code=LEGACY_JOB_UNSUPPORTED`，但仍无 tokenizer 与发布。事务冲突时已发布的最终 blob 不删除（并发事务可能已引用），因此数据库异常、profile 登记冲突或 PG 写入错误等路径可能留下孤儿文件。同一 `config_hash` 既有行字段与默认契约永久不一致的**确定性**孤儿路径已缓解：新上传在 publish 前只读预检该行并 fail closed，该内容不会被 publish（独立 reviewer P2 的确定性路径已缓解）；但这不是零孤儿——publish 后 PG 故障与预检/写事务间的先查后写竞态仍可能遗孤，旧孤儿未回收，也不能删除可能被并发事务共享的最终 blob。本切片没有 GC 作业，未实现配额与告警。

纯 Markdown 解析与切分已实现且不渲染 HTML：`html_block`/`html_inline` 被排除在正文之外，图片只取 alt，解析与切分绝不抓取或执行 URL。但解码后的 HTML 实体仍可能还原出字面 `<script>` 等文本，图片/链接里的危险 scheme URL 也可能作为字面原文留在 chunk 文本中；任何存储数据的展示必须按文本转义、绝不当作 HTML 执行，未来的原文预览与 HTML 输出必须消毒。

计划仍未实现：真实 MIME 嗅探、KB 配额、文件读取代理与预览 HTML 消毒、异步物理清理。文本 PDF 解析已实现但只限制页数（200）、单文件字节（20,000,000）与子进程硬时限（60 秒）。DOCX 收发已实现收窄子集的 ZIP 安全限额：受理期用标准库 ZIP 元数据快速拒绝非 PK/条目数 >512/声明累计解压 >64 MiB/单条 >1 MiB 且压缩比 >100/加密/绝对或 `..` 路径/反斜杠/NUL/重复名/缺必需部件/宏部件，worker 侧再用同一策略逐条有界流式实际读取并累计实际字节、校验 CRC 与拒绝 `<!DOCTYPE`/`<!ENTITY` 声明后再交给 `python-docx`；`python-docx==1.2.0` 自带的 XML 解析器已配置 `resolve_entities=False`，lxml 不联网，代码也不访问文档中的任何外链目标。**但仍未配置 rlimit/cgroup 级内存硬限，因此不声称进程内存隔离**；子进程只提供 60 秒硬时限与返回体上限。空/加密/损坏文档给出明确状态，不静默生成空索引。Markdown 或网页预览输出 HTML 前消毒。

静态网页导入只允许 http/https 和配置的演示域名；每次 DNS 解析及重定向都检查目标地址，限制出站网络、响应大小、超时和重定向次数。不能仅检查字符串前缀，也不允许登录、执行 JavaScript 或递归整站抓取。

## 模型与输出

外部文档只作为引用材料，内容中的命令、账号请求和工具调用指示不获得权限。MVP 不开放任意工具执行。证据和模型输出分别受 token/字节限制，回答按严格 schema 校验；未知引用 ID、非法类型和模型自造 URL/页码拒绝。没有证据或权限时尽量不调用生成模型。worker 侧本地真实 token 计数只用镜像内固定 revision 的 BGE tokenizer 四件：加载前逐文件核对大小与 SHA-256、文件集合多一个少一个都拒绝（`TokenCounterError`），运行时不联网、不记密钥、不把输入文本写入日志或账本；API 镜像不安装 `torch`，但自生成切片起安装了 `tokenizers==0.23.2` 用于离线加载 DeepSeek 生成预算的 tokenizer 产物（worker 侧的 BGE 计数同样依赖它），该 BGE 计数器已由默认关闭的真实入库管线在领取任务后调用（默认关闭时无任务调用）。关键词分析器也是纯本地模块（不联网、不读密钥、不改 jieba 全局状态）：jieba 基础 `dict.txt`（5,071,852 B + SHA-256）与 0 字节空领域词典都按原始字节核对后才初始化，分词器只在构造期独有的私有临时目录内建缓存并立即清理，绝不读写共享 `temp/jieba.cache`（该缓存对基础词典不做 mtime 校验，易被投毒）；运行时必须能创建可写私有临时目录（POSIX 0700、Windows per-user TEMP ACL），只读容器必须提供安全 tmpfs，否则静态 fail closed，不为可用性回退共享缓存。领域词典 v1 为空，不得用未授权或编造的企业术语填充；扩词典必须新建 index profile 并重索引，且未来 freq=0 词条会改全局 `jieba.finalseg.Force_Split_Words`，新词典版本须单独做安全评估。上述 tokenizer 资产校验与关键词分析器构造已由 worker 专用工厂 `rag_backend.ingestion.worker_index_identity.initialize_worker_index_identity` 在显式调用时组合执行：只调用一次 `Tokenizer.from_file`、只构造一次 `KeywordAnalyzer`，失败统一为静态脱敏的 `WorkerIndexIdentityError`，不把模型目录或词典路径写入错误消息；该工厂已由默认关闭的真实入库管线在领取任务后调用；独立 tester 已在真 worker 镜像内验收其资产校验与静态失败（两镜像各 99 断言全 pass），同样不核 inference 实际权重或 revision。

云 LLM 会收到问题与选中的授权片段。真实敏感材料只有在允许外发的策略下使用云服务，否则换内网模型。调用重排/LLM 前复核 ACL revision，回答交付前再次复核；撤权后已发出的字节无法追回，服务端只能停止后续调用/交付并记录事件。证据问答主流程已把这一约束落地：只把已入选的授权证据交给生成模型（无证据时直接拒答、不调用模型），模型前复核证据授权与版本，交付前再次复核，版本/删除/权限变化最多重新检索一次、持续变化返回 409 且不交付；业务客户端固定 `https://api.deepseek.com`、非流式、按请求显式发送 `thinking` 开关（默认关闭，不依赖供应商默认的思考开启）与开启时的 `reasoning_effort`、`trust_env=False`、零自动网络重试、有界响应体，整个网络调用期间不持有数据库连接或事务；模型名与思考强度只接受服务端白名单枚举（未验证模型返回 422 `GENERATION_OPTION_UNSUPPORTED`），客户端不能提交 endpoint 或任意模型名；思考模式返回的 `reasoning_content` 被丢弃，不进回答、不入库、不回显；模型只能返回临时 `E` 编号，来源 URL/页码/数据库 ID 由服务端从已保存 locator 映射，结构非法或无引用回答直接失败。追问改写复用同一受限客户端，但只把已授权历史轮次的**用户问题**与当前问题发给模型（历史助手回答不进入改写提示，避免把上一轮模型陈述当成事实），改写前先重新核查历史权限、每次 attempt 单独记录 `llm_usage` stage `qa_rewrite`；改写失败整轮失败且不自动重试，检索范围始终来自服务端会话 `kb_scope`。改写返回它实际入参的历史轮次，调用方在**首次检索前**、**每次版本变化重检索前**与**回答交付前**都重新鉴权这些来源：任一失效立即返回静态 409 `CONVERSATION_SOURCES_CHANGED`，不退化继续用派生独立问题，不发查询编码/关键词检索/回答，也不落派生问题（已发生的 `qa_rewrite` 账本保留）。结构化日志默认不记原文正文；审计和检索调试结果按权限过滤。

服务端记录实际 input/output tokens、模型、阶段和单价快照，分别核算在线、评估与重试。预算到 80% 提醒，到 100% 停止新生成，并为在途请求预留额度。限流和预算都在后端执行；HTTPX、Celery 与模型格式重试分别设有限次数、超时和总请求预算，防止重试相乘放大费用。证据问答主流程已实现其中一部分：每次真实 provider attempt（包括失败、超时与截断）都向 append-only `llm_usage` 追加一行（stage `qa_answer`，写入 provider 实际上报的 prompt/completion/缓存命中 token 与耗时），provider 未报告 usage 时只能是 `FAILED` 且 token 为空；本地 tokenizer 估算只落在 `query_run.estimated_input_tokens`，不写成 provider 事实；每轮实际使用的模型与思考选项另存在 `query_run.generation_options`（不被后续选择改写）；价格无可靠快照时四个价目/费用列为 NULL。输入目标已由本地预算执行（`LLM_INPUT_TOKEN_BUDGET` 默认 4,000），输出上限通过 provider `max_tokens` 传给 `LLM_OUTPUT_TOKEN_BUDGET`（默认 800）；因为上游无强制回传，provider 实际超出目标时不伪装成硬上限，而是如实记账并可在 `query_run`/`llm_usage` 对照。80%/100% 预算阈值与在途预留在本片仍未实现。

已实现的 `llm_usage` 是 append-only 事实表：一次 provider attempt 一行，失败、超时与凭据错误也追加，不更新、不删除；prompt/completion tokens 由 provider 报告，缺失时只能写 `FAILED`/`TIMEOUT` 且 token 与费用为 NULL，不允许篡改成功。写入用 api 运行角色（仅 SELECT+INSERT），worker 在本切片没有该表权限。一次性探针 `rag_backend.llm_probe` 默认关闭，只有显式设置 `ALLOW_LLM_PROBE=1` 并提供独立非占位 `LLM_API_KEY`（不复用开发期 Node Jev 的 `AI_GATEWAY_API_KEY`）时才向固定 `https://api.deepseek.com` 发一次请求；缺失任一项时快速失败、不联网不写账本。探针不把 prompt、响应正文或密钥写入数据库、日志或 marker，也不使用响应内容。单价与费用依赖缓存命中/未命中和高低峰价目，正确快照缺失时保持 NULL，因此 `llm_usage` 当前不能作为费用事实来源。探针在触网前只读预检目标库：连接角色必须是 `citemind_api`、`public.llm_usage` 存在且必要列可读、SELECT+INSERT 可用；未迁移、角色不符或权限不足都不触网。云调用与 PostgreSQL 提交无法原子化，预检后数据库故障仍可能使网络已发生而事实未落账，此时退出非零，不得视为连通验收成功。

生产网络只公开网关；PostgreSQL、Redis、inference 与文件卷不直接暴露公网。内部推理接口有凭证、批量限制和信号量。worker 侧受限 `InternalEmbeddingClient` 用 `INFERENCE_TOKEN`（SecretStr）作 Bearer，`trust_env=False` 使其不继承宿主 `HTTP(S)_PROXY`/自定义 CA、Bearer 不会随代理外发，`retries=0` 且**客户端自身零自动重试**；成功 200 用 `httpx` 流式读取，`Content-Length` 只做早拒、显式请求 `Accept-Encoding: identity` 并拒绝任何压缩编码、真实响应体上限 1 MiB，仅 503 读取有界 ≤4 KiB 错误体以区分机器码（`EMBEDDING_NOT_READY` 属服务未就绪、不可自动重试，`EMBEDDING_BUSY`/`EMBEDDING_QUEUE_TIMEOUT` 带 `Retry-After` 留给未来调用方决策，未知 503 静态 fail closed），其它非 200 不读正文，错误消息静态、不回显正文或输入；输入必须是 `Sequence[str]`，dict/bytes、逐项非 str 与孤立代理项都在网络前失败，基址拒绝控制字符；本地先做批量/字节/字符/token 预算，响应严格校验 512 维有限向量、`dimension`、冻结 `modelRevision` 与逐条 `tokenCounts`。Compose 中 `INFERENCE_TOKEN` 是 inference、worker 与 api（检索与问答的查询编码）共用的必填变量，三个服务的 Compose 环境都显式声明它；API 的 `Settings` 不配置该 token 时进程仍能启动，但任何一次检索/问答调用构造查询编码客户端时静态失败。该 worker 侧客户端已由默认关闭的真实入库管线在领取任务后构造使用（`INGEST_PROCESSING_ENABLED=0` 时不构造、不联网）；inference 不可用时按静态失败处理，运行期要求 inference 服务可用。inference 侧新增 `kind=query`：服务端在编码前恰好追加一次官方 instruction 前缀（契约 `bge-zh-query-v1`，不并入 `modelRevision`），token 计数与向量含前缀与特殊 token、不截断、超 512 返回 422，查询响应携带 `queryEncodingContract` 而 `kind=document` 响应省略该字段、路径不变；固定前缀与契约版本由独立 literal golden 测试钉死（回归检测，非自证）。API 侧另有受限查询客户端 `rag_backend.retrieval.query_embedding_client`：不导入 `tokenizers`/worker 身份，只发送原始查询文本（不追加、不去重前缀），同样 `trust_env=False`、`retries=0`、不跟随重定向、有界读取与静态脱敏错误，本地字符/字节上限按完整模型输入（前缀 + 用户查询）折算，并校验 512 维有限且 L2 归一化向量、`modelRevision` 一致、`queryEncodingContract` 精确等于 `bge-zh-query-v1`（缺失/非法/未知失败）与整数 1..512 的 `tokenCounts`；客户端零自动重试，单次请求重试归上层检索策略；该查询客户端与 inference 查询编码已由隔离模型 tester 在真实权重与真实 HTTP 上验收（`query(text)` 与 `document(prefix+text)` 向量逐元素差 0、token 相同；512 token 200、513 token 422 不截断；backend 真实客户端 23/23，含成功/revision 不匹配/timeout 与连接失败清理/close）；该客户端已由 `POST /api/v1/retrieval/search` 与证据问答主流程接线，每次检索按请求构造并在依赖退出时关闭，查询编码期间不持有数据库连接；检索路由/SQL/授权已实现首片，rerank 与相似度阈值仍未实现，证据问答（会话/历史/引用与生成）见本页上文。数据库账号按进程最小授权；若未来引入 PostgreSQL RLS，需要验证连接池身份设置和回收，不把启用 RLS 当作已验证的隔离。

## 配置与诊断日志

`Settings.database_url` 与 `Settings.redis_url` 是裸 `str`（后者为 `str | None`）字段，现已用 `Annotated[str, Field(repr=False)]` 让 `repr(Settings)`/`str(Settings)` 不再打印完整 DSN；该缓解已由独立 review 与独立 tester 在最终工作树验收（见 [开发约定](development.md)）。必须明确这是**仅针对 `repr(Settings)` 的局部单点防护，不是密码或 DSN 的整体保护**：字段的实际字符串值、连接行为与 `model_dump()` 输出都不变，以下路径仍可能泄漏——直接 `print(settings.database_url)`、`model_dump()`/`model_dump_json()`、`ValidationError.errors()` 中的 `input`，以及其他对象（异常、日志 record、测试报告等）携带或格式化 DSN 时的 `repr`。
