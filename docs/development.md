## 验证规则

- 对纯逻辑运行聚焦单测；授权 SQL、迁移和向量维度使用真实 PostgreSQL/pgvector；任务恢复使用真实 Redis 与独立 Celery worker。
- **自动化验收（Agent 默认路径，禁止读真实 `.env`）**：Agent 运行的集成/迁移验收一律**不得**读取仓库根 `.env`，也**不得**使用 `uv run --env-file .env ...`；加载真实 `.env` 会把真实凭据与 dev 关联 DSN 带进验收，不构成隔离证据。必须新建**独立命名**的 PostgreSQL/pgvector 与 Redis 容器（绝不操作 dev 六服务及其卷），使用**显式合成凭据**与**独立回环端口**，并在开跑前用 `docker port` 与一次只读连接核对宿主端口确实指向该隔离实例。测试进程只注入本轮所需的最小环境：`TEST_DATABASE_URL`、`TEST_MIGRATOR_DATABASE_URL`、`TEST_API_DATABASE_URL`、`TEST_WORKER_DATABASE_URL`（三者指向同一 `_test` 库）、`ALLOW_DESTRUCTIVE_TEST_DB=1`，以及需要 broker 时的 `TEST_REDIS_URL`（带合成密码、非 0 逻辑库）与 `ALLOW_TEST_REDIS=1`；同时显式清除从父进程继承的真实 provider 密钥与 dev 配置（至少 `LLM_API_KEY`、`ALLOW_LLM_PROBE`、`LLM_ENABLED`、`AI_GATEWAY_API_KEY`、`DATABASE_URL`、`REDIS_URL`、`INFERENCE_TOKEN`、`MIGRATION_DATABASE_URL`），只注入合成值，不修改父环境或真实配置。没有可用隔离环境时报告阻塞，绝不借 dev 六服务或真实 `.env` 凑数；测后删除自建容器与匿名卷。
- **人工授权流程（仅授权运维/用户手动执行）**：`uv run` 不会把根 `.env` 注入 `os.environ`，因此针对真实 dev/部署栈、依赖 `os.environ` 的人工命令（Alembic 在线迁移、Celery worker CLI、以及人工手动跑集成）由授权操作者显式写成 `uv run --env-file .env ...`；pydantic Settings 另行通过 `env_file=".env"` 读取同一文件，人工流程统一使用 `--env-file` 以保持两套来源一致。pydantic-settings 的读取优先级是「进程环境优先于 `.env`」：`DATABASE_URL`、`REDIS_URL`、`ENVIRONMENT`、`LLM_API_KEY`、`LLM_MODEL` 等均为无前缀裸名，若当前 shell 已有同名全局 export 会覆盖 `.env`。启动服务或运行显式 `ALLOW_LLM_PROBE=1` 的收费探针前，必须先确认这些同名变量与本项目意图一致；密钥可由运行环境注入（容器 env、CI secret 等），不要求只写在 `.env`，本仓库绝不要求回显或上传密钥。
- 对入库验证重复投递、Redis 断连或重启、worker 强制退出、租约过期后的迟到回写、旧版本继续可查和单次发布。
- 对问答验证越权内容从候选至引用全链不可见、撤权后的历史/下载、结构化回答和模型超时。性能与质量按 [评估与验收](evaluation.md) 的数据集和硬件条件实测。
- 当前可执行 `uv sync --frozen`、Ruff、mypy、非集成 pytest、Jev 脚本测试、Alembic 离线 SQL 检查和前端构建。真实 PostgreSQL/pgvector 集成测试需要 `TEST_DATABASE_URL`（`postgresql+psycopg` 驱动、数据库名以 `_test` 结尾）并显式确认 `ALLOW_DESTRUCTIVE_TEST_DB=1`，因为测试会执行 upgrade 和 downgrade；测试数据库必须由 CiteMind 独占、不能与其他应用共享，迁移账号必须拥有 `CREATE EXTENSION` 权限。运行前测试先断言 `current_database()` 与 URL 中的库名一致、`vector` 扩展不存在且 Alembic 处于 base，任何一项不满足都会失败而不是继续。未设置测试 DSN 时仅明确跳过。分角色镜像、依赖扫描、SBOM、GHCR 发布与恢复演练仍是后续计划。
- 在线迁移只接受显式 DSN：Alembic 配置项 `sqlalchemy.url` 优先，否则必须设置 `MIGRATION_DATABASE_URL`，缺失或不符合 SQLAlchemy URL 规则时直接以非零状态失败，不会回退到 `DATABASE_URL` 或开发默认 URL。该 DSN 需要 `CREATE EXTENSION` 权限，只用于迁移进程，不进入 API 与 worker 的运行配置。
- 离线 `uv run alembic upgrade head --sql` 只生成 SQL、不连接数据库，仍可使用开发默认 URL。
- 本地数据与服务切片用 `docker compose --env-file .env.example -f deploy/compose/compose.yml config --quiet` 做权威静态插值检查：不需要 Docker daemon，也不启动容器；pytest 中的部署文件测试只补充检查 digest、回环端口、初始化标记、必填变量在 `.env.example` 中以非空值提供和 LF 等源码不变量，不能替代 Compose CLI。首次真实启动前配置已忽略的根 `.env`，分两种情况：根 `.env` 不存在时用 `Copy-Item .env.example .env` 创建它并替换四个数据库/Redis 开发密码；根 `.env` 已存在时不得覆盖，只把 `.env.example` 中 Compose 需要的 `MIGRATION_DB_PASSWORD`、`API_DB_PASSWORD`、`WORKER_DB_PASSWORD`、`REDIS_PASSWORD` 四个密码变量、本地 worker/派发需要的 `REDIS_URL`、inference 需要的开发占位 `INFERENCE_TOKEN` 与可选的 `POSTGRES_PORT`、`REDIS_PORT`、`GATEWAY_PORT` 追加进去，已保存的 `AI_GATEWAY_API_KEY` 等本地配置保持原样。旧键 `CITEMIND_*` 已失效：若本地 `.env` 仍在使用旧名，必须在其中手动改名为裸名后重启，本仓库不读取也不代改本地 `.env`。
- inference 镜像的模型产物由 `inference/scripts/prepare_model.py` 在构建期从固定 revision 下载并校验证（Hub commit、Git blob/LFS 摘要与脚本内钉死 SHA-256），不在运行期下载。加载端 `load_embedder` 在导入 torch/transformers 之前复用包内 `citemind_inference.model_identity` 的同一组钉死摘要，离线核对六个产物的大小、SHA-256 与目录集合，并交叉核对模型目录父目录的 `model-manifest.json`；清单只作为待核对对象，不能自报身份，覆盖 `EMBEDDING_MODEL_PATH` 时同样走这套校验，任何偏差都使 lifespan 启动失败。离线复核用 `docker run --rm --network none --entrypoint python citemind-inference:latest scripts/prepare_model.py --verify`，离线真实编码用 `docker run --rm --network none --entrypoint python citemind-inference:latest -c "from citemind_inference.config import Settings; from citemind_inference.embeddings import load_embedder; e=load_embedder(Settings(inference_token='x')); v=e.embed(['离线样本'])[0]; print(e.dimension, e.model_revision, e.token_counts(['离线样本']), len(v), round(sum(x*x for x in v)**0.5, 9))"`。两者均不打印 token、不读取宿主模型卷。真实模型与独立 golden 的比较是显式 opt-in：在模型目录存在且清单校验通过时设 `RUN_MODEL_TESTS=1`（可用 `TEST_EMBEDDING_MODEL_PATH` 覆盖目录）后运行 `uv run --frozen pytest -q -m model tests/test_real_model.py`，token IDs 要求与 `tests/golden/golden-reference.json` 严格相等、512 维向量按每元素最大绝对差 ≤ 1e-4 比较；未 opt-in 时跳过，显式 opt-in 但模型缺失、损坏或 golden 不一致都必须失败。
- 根 `.env` 就绪后必须逐个核对连接串与 Compose 变量的完整一致性，任一项不符都会导致连接失败：`DATABASE_URL` 以及所有已启用的 migration/test DSN（`MIGRATION_DATABASE_URL`、`TEST_DATABASE_URL`、`TEST_MIGRATOR_DATABASE_URL`、`TEST_API_DATABASE_URL`、`TEST_WORKER_DATABASE_URL`）都要检查对应用户名、数据库名、host=`127.0.0.1`、端口=`POSTGRES_PORT` 与对应角色的密码，只有全部一致才能保持原样。允许在本地安全比对，但不得把真实密码输出到终端、日志或命令历史，只报告是否一致。
- `POSTGRES_PORT` 变化只改变 PostgreSQL 的宿主端口，因此只需把上述每个 DSN 的端口同步为新值，用户名、数据库名和密码无需改动。同步后重新执行已有单行 `docker compose --env-file .env -f deploy/compose/compose.yml up -d --wait` 以重建容器；命名卷保留数据，不需要 `down -v`。
- PostgreSQL 初始化流程写入 `MIGRATION_DB_PASSWORD`、`API_DB_PASSWORD`、`WORKER_DB_PASSWORD` 三个角色密码（分别对应 `citemind_migrator`、`citemind_api`、`citemind_worker`）。initdb 脚本只在空命名卷上执行一次，所以卷已初始化后再改动其中任一密码，重启不会更新已有角色：必须先执行会删除本地数据库数据的 `docker compose --env-file .env -f deploy/compose/compose.yml down -v`，再执行 `docker compose --env-file .env -f deploy/compose/compose.yml up -d --wait`，让 initdb 重建角色、密码与 ACL。角色或 ACL 需要重建时同样先跑 `down -v`。
- Redis 密码 `REDIS_PASSWORD` 不进入任何 PostgreSQL DSN，也不参与上面的 DSN 同步：它只需在 Compose 的 redis 环境变量与 `--requirepass` 之间保持一致，重建 redis 容器即可生效，不需要 `down -v`。worker 与本地派发使用的 `REDIS_URL` 只与 `REDIS_PASSWORD`、`REDIS_PORT`（宿主）或 Compose 内 `redis:6379`（容器）一致；缺失时 worker 启动直接失败，不回退到 localhost。
- 缺少任一密码变量时 `docker compose --env-file .env -f deploy/compose/compose.yml up -d --wait` 会以 `required variable ... is missing a value` 退出，这是必填插值的预期快速失败，不是 Compose 故障。
- `docker compose config` 会把插值后的密码明文打印，Redis 密码也会出现在容器命令中；不要分享这些输出，生产部署必须改用独立密钥方案。
- 验证 Redis 是否真的要求鉴权时必须临时移除 `REDISCLI_AUTH`：该变量由 Compose 注入 redis 容器，容器内 `redis-cli` 会继承它并自动完成 AUTH，继承环境下 `PING` 返回 `PONG` 不能证明 Redis 没有密码。在 PowerShell 中执行 `docker compose --env-file .env -f deploy/compose/compose.yml exec -T redis env -u REDISCLI_AUTH redis-cli -e ping`，`env -u` 只对这一次 `redis-cli` 子进程取消 `REDISCLI_AUTH`（不要把变量设为空值），`-e` 让 `redis-cli` 在收到错误回复时以非零状态退出；预期 `NOAUTH Authentication required.` 文本写入 stderr（不是 stdout）且退出码非零，只有观察到二者才能确认鉴权生效。
- 角色权限集成测试是只读的，但要求三个角色 DSN 同时提供并指向同一个 `_test` 库：`TEST_MIGRATOR_DATABASE_URL`、`TEST_API_DATABASE_URL`、`TEST_WORKER_DATABASE_URL`，用户名固定为 `citemind_migrator`、`citemind_api`、`citemind_worker`。若测试库名为 `<app>_test`，验收同时要求对应的 `<app>` 应用库存在并核对两个库的 ACL，避免范围静默缩小。三者都未设置时明确跳过；只设置部分、或驱动、用户名、host、port、database 任一项不符时在连接前失败，不尝试连接。
- 真实 Redis broker 集成测试需要 `TEST_REDIS_URL`（`redis`/`rediss` scheme、host 必须是回环地址、必须带密码、必须显式指定非 0 逻辑库如 `.../15`）并显式设置 `ALLOW_TEST_REDIS=1`。未设置 DSN 时明确跳过；DSN 非法或缺少 opt-in 时在连接前失败，不尝试连接。测试以唯一队列名派发 `rag_backend.probe`，把临时 marker 目录传给 worker 子进程，只在 `finally` 删除本次运行自己的队列 key 及其 `_kombu.binding.<queue>`、不 `FLUSHDB`，并回收 worker 子进程；该清理只覆盖本次运行，套件不保证 Redis 逻辑库自动归零，旧 suite 可能留下 `_kombu.binding.<queue>` 等绑定键；本片最终验收时 tester 在自身独占的 db15 上手动 `FLUSHDB` 清掉 3 个 kombu 键，这套件之外的收尾不能被当成套件行为。执行证据来自与本次 `async_result.id` 对应的 marker 文件；worker 日志与 `inspect` 只用于 readiness 与失败诊断，不使用 Celery result backend。
- 一次性云 LLM 探针是显式 opt-in 的运维入口，不是业务 API：只有 `ALLOW_LLM_PROBE=1` 与真实 `LLM_API_KEY` 同时可用（来自进程环境或根 `.env`，pydantic-settings 进程环境优先）时才允许运行；进程环境里的 `LLM_API_KEY` 同样会用于向固定 `https://api.deepseek.com` 请求，运行前必须确认当前 shell 的同名变量确为本项目密钥，且绝不回显或上传它（不复用开发期 Node Jev 的 `AI_GATEWAY_API_KEY`，后者不应进入 api/worker）。两者任缺时快速失败、不联网、不写账本，且不会探测数据库。
- 运行探针前必须让**目标库**（由 `DATABASE_URL` 指定的 api 角色 DSN）已应用包含 `llm_usage` 的迁移（`20260923_0004` 及之后的 head，当前 dev 库为 `20260923_0005`）；探针预检以 `public.llm_usage` 的表结构和角色权限为准，不核对精确 revision。迁移会改写目标库：`uv run --env-file .env alembic upgrade head` 需要 `MIGRATION_DATABASE_URL`（高权限 migrator DSN），**不要**照抄到生产库；生产须先备份、确认专用库，并用独立迁移进程执行，本仓库不代为运行。探针自身在触网前会做只读预检：连接角色必须是 `citemind_api`、`public.llm_usage` 必须存在且必要列可读、SELECT+INSERT 权限可用；未迁移、角色不符、权限不足或目标库不可达都会以退出码 6 快速失败（其中 PostgreSQL 连接建立的上限为 5 秒，只约束建连，不限制已建立连接上 SQL 读写的语句执行时长），且不联网、不写账本。预检通过后数据库仍可能故障：云调用与 PostgreSQL 提交无法原子化，网络之后写入失败会返回非零且可能没有账本行，绝不谎报成功。
- 预检与 opt-in/密钥都满足后，探针用固定请求向 `https://api.deepseek.com` 的 chat completions 发一次请求（`max_tokens` 极小、超时短暂、网络重试为 0），单行命令 `uv run python -m rag_backend.llm_probe`。探针直连 DeepSeek，显式不继承 `HTTP(S)_PROXY`、`SSL_CERT_FILE` 与 `SSL_CERT_DIR`；宿主必须能直连外网，若网络只能经代理，探针会以连接失败返回非零，不会静默改走代理或改用自定义 CA。只有 200–299 视为候选成功；3xx 与其他非 2xx 一律写 `FAILED` 与 `HTTP_<状态码>`。provider `usage` 缺失写 `MISSING_USAGE`，出现 bool 或负数（含缓存 token）写 `INVALID_USAGE`，两种情况四个 token 字段全为 NULL，不靠数据库 CHECK 报错。退出 0 仅当 provider 报告的 prompt/completion tokens 之和大于 0，且已以 api 角色写入并回读 `llm_usage` 的 `PROVIDER_REPORTED` 事实；HTTP 错误、超时、网络失败写 `FAILED`/`TIMEOUT` 并返回非零；provider 成功但账本写入或回读失败也返回非零。探针不记录 prompt、响应正文与密钥。`thinking` 显式设为 disabled；未添加 `reasoning_effort`，一次真实计费调用已确认该请求形态可成功返回 provider usage（见本节实测表）。单价与费用依赖缓存命中/未命中和高低峰，正确快照缺失时保持 NULL，`llm_usage` 不是费用事实源。
- Linux Compose 的确定性 worker 验收走 override：`docker compose --env-file .env -f deploy/compose/compose.yml -f deploy/compose/queue.yml up --build --abort-on-container-exit --exit-code-from queue-probe queue-probe`。命令显式只启动 `queue-probe` service，Compose 自动带上它依赖的 worker/redis/postgres，避免六服务里其它容器干扰 `--abort-on-container-exit`。它给 base worker 与一次性 `queue-probe` 挂载同一个非 root marker 卷并设置 `PROBE_MARKER_DIRECTORY`；`queue-probe` 派发唯一 probe 后只在受信目录里等待并校验 marker，成功退出 0、失败/超时退出非 0，因此可用 `--exit-code-from queue-probe` 得到硬证据。该 override 不引入 result backend，base compose 默认不运行 queue-probe。验收后回收容器与网络（保留所有命名卷）：`docker compose --env-file .env -f deploy/compose/compose.yml -f deploy/compose/queue.yml down --remove-orphans`；如需单独删除 queue-probe 的 marker 卷，用 `docker volume rm citemind_probe-markers`，不要用 `down -v`，它会一并删除数据库与 Redis 数据。
- 宿主上验收回环地址（如 `http://127.0.0.1:58080/api/v1/health`）的 HTTP 命令必须绕过代理：PowerShell 用 `curl.exe --noproxy "*" -fsS http://127.0.0.1:58080/api/v1/health`。若 shell 设置了 `HTTP_PROXY`/`HTTPS_PROXY`，回环请求可能被送到代理并返回代理自身的 502，形成伪证据；用 `curl.exe` 而不是 `curl`，因为 PowerShell 的 `curl` 是 `Invoke-WebRequest` 别名。

## 当前命令

> 警示：下面两条命令使用不同 DSN，各自作用于自己指向的目标库。`uv run --env-file .env alembic upgrade head` 只读取 `MIGRATION_DATABASE_URL`（高权限 migrator DSN），在线模式**绝不**回退到 `DATABASE_URL`；`uv run python -m rag_backend.llm_probe` 读取 `DATABASE_URL`（api 角色 DSN）。运行前确认两者指向同一个目标库；迁移会改写该库，生产必须先备份、使用专用库并保留独立 migrator DSN，不要照抄；探针会发一次真实云请求并可能产生费用（需 `ALLOW_LLM_PROBE=1` 与独立密钥）。探针在触网前会拒绝未迁移或角色/权限不符的目标库。

以下命令均从仓库根目录执行。其中带 `--env-file .env` 的条目属于**人工授权流程**，只由授权运维在确认真实目标库/密钥后手动执行；Agent 自动化验收禁止使用它们，必须按“验证规则”新建隔离合成容器并以显式 `TEST_*`/`ALLOW_*` 环境变量运行：

```powershell
uv sync --frozen
uv run uvicorn rag_backend.main:app --reload --loop rag_backend.event_loop:create_event_loop
uv run ruff check backend/src migrations tests
uv run mypy
uv run pytest -m "not integration"
uv run alembic heads
uv run alembic upgrade head --sql
uv run --env-file .env alembic upgrade head
uv run python -m rag_backend.llm_probe
uv run python -m rag_backend.auth.cli --username <name>
uv run python -m rag_backend.auth.cli --username <name> --password-env NEW_USER_PASSWORD
uv run --env-file .env pytest -m integration
uv run --env-file .env celery -A rag_backend.worker:celery_app worker --pool=solo --loglevel=INFO
docker compose --env-file .env -f deploy/compose/compose.yml -f deploy/compose/queue.yml config --quiet
docker compose --env-file .env.example -f deploy/compose/compose.yml config --quiet
docker build -f deploy/compose/Dockerfile --target api --tag citemind-api:verify .
docker run --rm --network none --entrypoint python citemind-api:verify backend/scripts/prepare_generation_tokenizer.py --verify
docker compose --env-file .env -f deploy/compose/compose.yml up -d --build --wait
docker compose --env-file .env -f deploy/compose/compose.yml exec -T worker celery -A rag_backend.worker:celery_app inspect ping
docker compose --env-file .env -f deploy/compose/compose.yml -f deploy/compose/queue.yml up --build --abort-on-container-exit --exit-code-from queue-probe queue-probe
docker compose --env-file .env -f deploy/compose/compose.yml -f deploy/compose/queue.yml down --remove-orphans
pnpm install --frozen-lockfile
pnpm test:jev
pnpm jev -- scripts/jev-request.example.json
pnpm --dir frontend dev
pnpm frontend:build
```

`pnpm jev` 从标准输入或首个参数指定的 JSON 文件读取 `{ state, questions }`，固定调用 `typesafe-ai/jev`；输入只应包含完成当前判断所需的非敏感状态。提交前检查差异、生成文件和密钥，只报告实际运行结果与未运行的验证。

Celery worker 的权威验收环境是 Linux 容器或 WSL2：`docker compose --env-file .env -f deploy/compose/compose.yml up -d --wait` 会启动独立 `worker` 容器，其 healthcheck 用 `inspect ping` 确认消费。确定性执行验收用 `deploy/compose/queue.yml` 的 queue-probe 退出码，而不是日志或事件。Windows 本机只能用 `--pool=solo`（默认 prefork 不受支持），适合开发自检，不等同于 Linux 上的并发与故障恢复验收。
